# 大文件入库方案（book/ 与 Git LFS）

> **状态**：已实施 ｜ **日期**：2026-10-11 ｜ **触发**：首次推送被 Git 大文件告警拦截
>
> 相关：[资源分类与 OSS 方案](01-资源分类与OSS方案.md) · [来源台账](来源台账.md) · [`.gitattributes`](../../.gitattributes)

---

## 1. 问题

首次推送到 `github.com/edxspark/spark-nhx-master` 时报错：

```
You are about to commit a large file into the repository: 1 file with the total size of 63MB.
It is not recommended to store large files in a Git repository. Consider using Git LFS
```

⚠️ **这个报错严重低估了规模**——工具逐文件检查，遇到第一个超限文件（63.9 MB 的
`人纪系列黄帝内经上册.pdf`）就停下。实测暂存区真实情况：

| 指标 | 实测值 |
|---|---|
| 暂存区文件数 | **264 个** |
| 暂存区总体积 | **696.9 MB** |
| 其中 > 10 MB 的文件 | **19 个，合计 626.0 MB** |

### 体积构成（修复前）

| 类型 | 个数 | 体积 | 占比 |
|---|---|---|---|
| `.pdf` | 18 | 595.8 MB | 85.5% |
| `.backup/*.bak` | 36 | 60.8 MB | 8.7% |
| `.html`（OCR 全文） | 18 | 31.1 MB | 4.5% |
| `.json` / `.md` / `.txt` / `.png` | 52 | 3.0 MB | 0.4% |

**94% 的体积来自 `book/` 下的 PDF 本体与 HTML 备份副本。**

### 为什么必须处理（两条独立依据）

1. **仓库自身红线**：`01-资源分类与OSS方案.md` 第 22 行明确
   「单文件 > 50 MB、仓库 > 1 GB 会显著拖慢克隆与检索」；第 10 行确立
   「小文件入库（Git），大文件上云（OSS），中间只放索引」。696.9 MB 的首次提交
   会直接吃掉这条红线的大半。
2. **公开仓库 + 版权内容**：远端 `edxspark/spark-nhx-master` 为 **PUBLIC**。
   `book/` 是倪海厦先生人纪/天纪系列**正式出版书籍**的扫描 PDF 与 OCR 全文，
   推送到公开仓库等于公开分发受版权保护的作品。

### 一个关键的好消息：历史是干净的

```console
$ git ls-tree -r -l HEAD | awk '{s+=$4} END {printf "%.1f MB / %d files\n", s/1048576, NR}'
0.0 MB / 1 files          # HEAD 只有一个 19 字节的 README.md
$ git rev-list --objects --all | ... | awk '$2>10485760'   # 无任何 >10MB 的 blob
```

**没有任何大 blob 进入过提交历史**，因此本次修复**无需重写历史、无需 force push**。
这一点很重要：一旦首次 push 成功，596 MB 版权书籍就会永久留在公开历史里，
届时只能靠 `git filter-repo` + force push 补救。

## 2. 决策

| 对象 | 处置 | 理由 |
|---|---|---|
| `book/**/*.pdf`（18 个，595.8 MB） | **Git LFS 追踪** | 保留书籍本体与可复现的 OCR 源稿，同时不让二进制膨胀普通 Git 历史 |
| `book/**/*.html`（18 个，31.1 MB） | **不入库**（`.gitignore`） | 是受版权书籍的**可搜索全文**，进公开仓库的风险高于 PDF 本体（会被搜索引擎索引） |
| `book/**/.backup/`（36 个，60.8 MB） | **不入库**（`.gitignore`） | 同为 HTML 全文副本，且可由 `scripts/repair_books.py` 再生 |
| `book/**/*.{md,json,txt}` + `.acceptance/*.png` | **入库** | 整理产物与验收证据，符合「中间只放索引」 |
| 其余 190 个文件（`src/` `docs/` `knowledge/` 等） | **入库** | 纯文本，合计 9.2 MB |

### 为什么 PDF 用 LFS 而不是 OSS

`media/` 走的是「本体在 OSS，索引在 Git」（`AGENTS.md` §6.6）。书籍 PDF 的体量
（595.8 MB）本可同样上云，但本次选择 LFS 的理由是**保留 OCR 源稿的可复现性**：
`book/` 的整理成果（`repair_applied.json`、`OCR错字清单.md`）需要能回溯到具体源稿。
这是一次**有意识的偏离**，记录在此以便日后复核。

> **残余风险（未消除）**：LFS 只是改变了存储方式，**没有解决公开分发问题**。
> GitHub LFS 免费额度为 1 GB 存储 + 1 GB/月流量，595.8 MB 已占约 60%。
> 若后续要提高合规水位，建议二选一：
> ① 将仓库转为 private；② 改为 OSS 承载 PDF 本体（同 `media/`），Git 只留索引。

## 5. 克隆者须知

```bash
git clone https://github.com/edxspark/spark-nhx-master.git
cd spark-nhx-master
git lfs pull                      # 拉取 595.8 MB 的 PDF 本体；未装 git-lfs 时只会得到指针文件
```

- **未安装 `git-lfs`** 时，`book/**/*.pdf` 会是指针文本文件而非 PDF。
  安装：`brew install git-lfs && git lfs install`
- **`book/*.html` 与 `book/*/.backup/` 不在仓库里**，克隆后不存在。
  因此 `python3 scripts/verify_books.py` 在全新克隆上**无法运行**（会报「找不到备份」）。
  该书稿验收依赖本地工作副本，这是本次决策的已知代价。

## 6. 回滚方法

若需要恢复「全部入普通 Git」的旧状态：

```bash
git rm --cached -r book .gitattributes        # 撤出暂存
rm .gitattributes
# 删除 .gitignore 中 book/**/*.html 与 book/**/.backup/ 两条
git add book/
```

若已 push 且需要把 PDF 从历史中彻底抹除，需用 `git filter-repo` 重写并 force push——
**这正是本次抢在首次 push 前修复所避免的成本。**
