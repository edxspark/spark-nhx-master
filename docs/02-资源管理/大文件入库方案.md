# 大文件入库方案（book/ 与 Git LFS）

> **状态**：已实施 ｜ **日期**：2026-10-11 ｜ **触发**：首次推送被 Git 大文件告警拦截
>
> 相关：[资源分类与 OSS 方案](01-资源分类与OSS方案.md) · [来源台账](来源台账.md) · [`.gitattributes`](../../.gitattributes)

---

## 1. 问题

首次推送到 `github.com/edxspark/spark-nhx-master` 时报错：

```
You are about to commit a large file into the repository: 1 file with the total size of 63MB.
It is not recommended to store large files in a Git repository. Consider using Git LFS
```

⚠️ **这个报错严重低估了规模**——工具逐文件检查，遇到第一个超限文件（63.9 MB 的
`人纪系列黄帝内经上册.pdf`）就停下。实测暂存区真实情况：

| 指标 | 实测值 |
|---|---|
| 暂存区文件数 | **264 个** |
| 暂存区总体积 | **696.9 MB** |
| 其中 > 10 MB 的文件 | **19 个，合计 626.0 MB** |

### 体积构成（修复前）

| 类型 | 个数 | 体积 | 占比 |
|---|---|---|---|
| `.pdf` | 18 | 595.8 MB | 85.5% |
| `.backup/*.bak` | 36 | 60.8 MB | 8.7% |
| `.html`（OCR 全文） | 18 | 31.1 MB | 4.5% |
| `.json` / `.md` / `.txt` / `.png` | 52 | 3.0 MB | 0.4% |

**94% 的体积来自 `book/` 下的 PDF 本体与 HTML 备份副本。**

### 为什么必须处理（两条独立依据）

1. **仓库自身红线**：`01-资源分类与OSS方案.md` 第 22 行明确
   「单文件 > 50 MB、仓库 > 1 GB 会显著拖慢克隆与检索」；第 10 行确立
   「小文件入库（Git），大文件上云（OSS），中间只放索引」。696.9 MB 的首次提交
   会直接吃掉这条红线的大半。
2. **公开仓库 + 版权内容**：远端 `edxspark/spark-nhx-master` 为 **PUBLIC**。
   `book/` 是倪海厦先生人纪/天纪系列**正式出版书籍**的扫描 PDF 与 OCR 全文，
   推送到公开仓库等于公开分发受版权保护的作品。

### 一个关键的好消息：历史是干净的

```console
$ git ls-tree -r -l HEAD | awk '{s+=$4} END {printf "%.1f MB / %d files\n", s/1048576, NR}'
0.0 MB / 1 files          # HEAD 只有一个 19 字节的 README.md
$ git rev-list --objects --all | ... | awk '$2>10485760'   # 无任何 >10MB 的 blob
```

**没有任何大 blob 进入过提交历史**，因此本次修复**无需重写历史、无需 force push**。
这一点很重要：一旦首次 push 成功，596 MB 版权书籍就会永久留在公开历史里，
届时只能靠 `git filter-repo` + force push 补救。

## 2. 决策

| 对象 | 处置 | 理由 |
|---|---|---|
| `book/**/*.pdf`（18 个，595.8 MB） | **Git LFS 追踪** | 保留书籍本体与可复现的 OCR 源稿，同时不让二进制膨胀普通 Git 历史 |
| `book/**/*.html`（18 个，31.1 MB） | **入库**（普通 Git） | 属「书籍文本」，需 diff 与追溯；单文件最大 11.75 MB，未触 50 MB 红线。⚠️ 曾一度排除，后经决策方改回，见 §2.1 |
| `book/**/.backup/`（36 个，60.8 MB） | **不入库**（`.gitignore`） | 同为 HTML 全文副本，且可由 `scripts/repair_books.py` 再生 |
| `book/**/*.{md,json,txt}` + `.acceptance/*.png` | **入库** | 整理产物与验收证据，符合「中间只放索引」 |
| 其余 190 个文件（`src/` `docs/` `knowledge/` 等） | **入库** | 纯文本，合计 9.2 MB |

### 2.1 决策变更：OCR 全文 HTML 改判为入库

**初判**（20:00 提交 `6abf49c`）：`book/**/*.html` 不入库，理由是其为受版权书籍的
可搜索全文，进公开仓库会被搜索引擎索引，风险高于 PDF 本体。

**改判**（20:0x，决策方要求）：**HTML 入库**。

改判依据：HTML 是 `book/` 整理工作的**工作面**——`scripts/repair_books.py`
与 `repair_toc.py` 直接改写它，`OCR错字清单.md`、`目录整理报告.md` 都是它的派生结论。
不版本化则「正文一个字不改」这一原则无法 review，整理成果失去可追溯性
（违反 `AGENTS.md` §7.1「产物落盘、可追溯、可回滚」）。

**已知代价与残余风险**（决策方已知悉并接受）：

- 18 个文件的全文将出现在 **PUBLIC** 仓库，可被搜索引擎与第三方索引。
- 全文与 PDF 本体现在都在公开仓库中，**版权分发风险由 LFS 的「换存储」变成了「换存储 + 公开全文」**。
- 若后续要提高合规水位，唯一有效动作是把仓库转为 private，或把 `book/` 整体改为
  OSS + 本地保留。**仅调 `.gitignore` 已不足够**——历史里已经有了。

> 本节的写法遵循「不确定就标注」：这是一次**由决策方拍板的取舍**，
> 不是技术上的更优解。记录在此以便日后复核。

### 为什么 PDF 用 LFS 而不是 OSS

`media/` 走的是「本体在 OSS，索引在 Git」（`AGENTS.md` §6.6）。书籍 PDF 的体量
（595.8 MB）本可同样上云，但本次选择 LFS 的理由是**保留 OCR 源稿的可复现性**：
`book/` 的整理成果（`repair_applied.json`、`OCR错字清单.md`）需要能回溯到具体源稿。
这是一次**有意识的偏离**，记录在此以便日后复核。

> **残余风险（未消除）**：LFS 只是改变了存储方式，**没有解决公开分发问题**。
> GitHub LFS 免费额度为 1 GB 存储 + 1 GB/月流量，595.8 MB 已占约 60%。
> 若后续要提高合规水位，建议二选一：
> ① 将仓库转为 private；② 改为 OSS 承载 PDF 本体（同 `media/`），Git 只留索引。

### 3.1 一次工作区丢失事件（须记录）

在 `6abf49c` 提交**之后**、本文件成稿之前，工作区发生过一次**本次 Git 修复之外**的删除：

| 时间 | 对象 | 后果 |
|---|---|---|
| 20:00:27–20:00:37 | `book/{3黄帝内经,4伤寒论,5金匮要略,6天纪}/.backup/` | 34 个 `.bak` 消失（约 58 MB） |
| 20:03:22 | `.gitignore` | `book/**/*.html` 排除条被移除 |
| 20:03:52 | `book/.audit/`、`book/.acceptance/` | 10 个文件消失 |

- `.audit/` 与 `.acceptance/` 的 10 个文件**已从提交 `6abf49c` 恢复**（`git restore --source=HEAD`）。
- `.bak` **从未进入任何提交**（`git log --all -- 'book/**/.backup/*'` 无输出），
  **无法从 git 恢复**；若为 Finder 删除，可查 macOS 废纸篓。
- **后果**：`python3 scripts/verify_books.py` 现为 **18 个文件 17 个失败**
  （只剩 `1针灸` 的备份幸存），「正文零改动」不再可验证。
  若 `.bak` 无法找回，需从 PDF 重新 OCR 才能重建基线。

> 该事件与本次 Git 修复无关：`git rm -r --cached` 只作用于索引、不动工作区；
> 删除发生在提交之后，彼时磁盘上仍能数到 30 个 `.bak`。

## 4. 验收证据

### 4.1 体积（修复前 → 修复后，按 index blob 实测）

```console
$ git ls-files -z | while IFS= read -r -d '' f; do
    git cat-file -s "$(git ls-files -s -- "$f" | awk '{print $2}')"
  done | awk '{s+=$1} END {...}'

修复前（全量在普通 Git）：总计 696.9 MB / 264 个文件
修复后（仅排除 .backup）：总计   9.16 MB / 211 个文件
最终（HTML 按 §2.1 改判入库）：总计 40.33 MB / 230 个文件    # 相对修复前 -94.2%

$ # 暂存区中 >1MB 的文件
修复前：19 个（最大 63.9 MB）
最终：4 个（最大 11.75 MB，全部为 OCR 全文 HTML，未触 50 MB 红线）
```

> 40.33 MB 中，PDF 已不在普通 Git 内——它们以 LFS 指针形式占用不到 2 KB，
> 595.8 MB 的实际内容存放在 LFS 存储。

### 4.2 PDF 确实以 LFS 指针存储

```console
$ git lfs ls-files | wc -l
18

$ git cat-file -p ":book/3黄帝内经/人纪系列黄帝内经上册.pdf" | head -3

oid sha256:8bae5712d17d2e03e5ea148032e8f7429f7f449e65fffe614be16c9804cb7718

```

### 4.3 `book/` 的处置未破坏验收契约

`scripts/verify.sh` 的 11 个检查段**没有一段读 `book/`**，实测通过（见 §4.4）。
`scripts/verify_books.py` 是独立脚本，在 `.bak` 丢失**之前**实测：

```console
$ python3 scripts/verify_books.py
汇总：18 个文件，0 个失败          # 退出码 0
```

⚠️ 该脚本**现已降级**为 `18 个文件，17 个失败`，原因是 §3.1 的 `.bak` 丢失事件，
**与本次 Git 修复无关**。

## 5. 克隆者须知

```bash
git clone https://github.com/edxspark/spark-nhx-master.git
cd spark-nhx-master
git lfs pull                      # 拉取 595.8 MB 的 PDF 本体；未装 git-lfs 时只会得到指针文件
```

- **未安装 `git-lfs`** 时，`book/**/*.pdf` 会是指针文本文件而非 PDF。
  安装：`brew install git-lfs && git lfs install`
- **`book/*/.backup/` 不在仓库里**，克隆后不存在。
  因此 `python3 scripts/verify_books.py` 在全新克隆上**无法运行**（会报「找不到备份」），
  即使本地有原工作副本也同样如此——本地那 34 个 `.bak` 已经丢了（§3.1）。
  该书稿验收基线需要重建。
- `book/**/*.html` 是入库的（§2.1），克隆后即可 review 整理成果本身。

## 6. 回滚方法

若需要恢复「`book/` 全部不入库」的旧状态：

```bash
git rm --cached -r book/.audit book/.acceptance
# 在 .gitignore 中加回 book/**/*.html
git add .gitignore
```

若需要把 PDF 从 LFS 改回普通 Git（不推荐，会重新触碰 50 MB 红线）：

```bash
rm .gitattributes
git rm --cached -r book && git add book/
```

若已 push 且需要把 PDF 从历史中彻底抹除，需用 `git filter-repo` 重写并 force push——
**这正是本次抢在首次 push 前修复所避免的成本。**
