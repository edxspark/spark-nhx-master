## 9. 白屏与登录失败排障（2026-10-11 实测）

### 9.1 `http://0.0.0.0:18790` 页面全白

| 项 | 值 |
|---|---|
| 现象 | 页面完全空白，`document.title` 为空，`document.body.innerHTML` 长度 0 |
| 服务器 | 日志显示 200，静态资源全部正常（HTML 3687 / CSS 11213 / JS 15454 字节） |
| 根因 | **`0.0.0.0` 是绑定地址，不是访问地址。Chrome 128+ 屏蔽对它的导航与 fetch**（防 DNS rebinding）。实测 `fetch('http://0.0.0.0:18790/api/health')` 返回 **200 但 body 为空** |
| 修复 | 访问改 `http://127.0.0.1:18790`；服务启动日志改为打印**可访问地址**（`browsable_urls()`） |

### 9.2 登录必定失败（严重）

```
服务日志：
[nhx] "POST /api/chat HTTP/1.1" 401
[nhx] "{"text":"桂枝汤的组成是什么","session_id":null}POST /api/auth/login HTTP/1.1" 501
```

| 项 | 内容 |
|---|---|
| 现象 | 未登录点发送 → 401 → 弹登录框 → **登录必失败**，前端报 `Unexpected token '<', "<!DOCTYPE "... is not valid JSON` |
| 根因 | **401 响应在读取请求体之前就发出了**，未读字节留在 socket；浏览器复用同一条 keep-alive 连接发登录请求时，服务器把残留 body 当成了请求行 → `501` → 返回 HTML |
| 影响面 | 任何「未读 body 就回 4xx」的路径（401/403/404/400）都会污染下一条请求 |
| 修复 | 加 `_drain_body()`：**所有错误分支先读完请求体再回响应**；`nhx_app/server.py` 与 `nhx_media/server.py` 都已修 |
| 验证 | 修复后同一序列日志为 `401` → `200`，无 501、无拼接请求行 |

### 9.3 顺带修复

- **端口被占用**：原为裸 traceback，现给出占用查询/结束/换端口的可操作指引
- **结构化条目被截断**：方剂/本草只给 220 字片段，模型无法逐字复述组成，
  实测响应里明确说「检索出来的方剂库记录是截断的」并拒绝补全——
  姿态正确，但根因是我们没给全材料。现改为**结构化条目整条给出**（限 8000 字符），
  经典原文仍用片段（体量大）。

## 10. 原文检索失效与修复（2026-10-11）

### 10.1 现象

问「伤寒论第 12 条讲什么」，模型回答：

> 先说实话：这条我手上没有。你问第 12 条，我这次检索回来的材料里没有第 12 条。
> 返回的是：《伤寒论》第 110～112 条一带的片段……所以按规矩——我不给你默写第 12 条的原文。

**模型的姿态完全正确**（拒绝凭记忆补写古文，符合 R1），但**检索是坏的**。

### 10.2 根因

`knowledge/01-人纪-中医经典/04-伤寒论/原文/伤寒论-条文.json` 里 398 条被索引成**一个大文本块**，
关键词/二元组打分只会在这个块里挑一个片段返回——**"第 12 条" 这个查询对打分毫无区分度**。

这正是 `AGENT.md §5` 检索原则一写的问题：**原文走精确、讲解走语义**。
原则写了，但管线里没实现。

### 10.3 修复

在 `kb.py` 中实现条号解析与精确取原文：

| 环节 | 实现 |
|---|---|
| 条号识别 | `extract_article_refs()` — 支持「第12条」「第十二条」「第 12 条」「12条」 |
| 中文数字 | `cn_to_int()` — 支持 一二三…十…百（九十六→96，三百九十八→398） |
| 精确取原文 | `_exact_articles()` 走 `find_article()`，标注「原文原样，可直接引用」 |
| 抑制噪音 | 命中条号时**丢弃经典原文的关键词片段**——那些片段正是"问 12 条返回 110 条"的元凶 |
| 保留补充 | 方剂/本草等结构化条目保留（无条号混淆问题，且常是必要补充） |
| 未收录处理 | 明确写「知识库中未找到该条——请如实说明『未收录』，不要凭记忆补写原文」 |

### 10.4 修复后验证

| 查询 | 结果 |

## 11. 服务被 SIGTERM 与进程管理

### 11.1 现象

用 `python3 src/nhx_app/server.py &` 起的服务，在启动它的 shell 退出后被杀（exit 143 = SIGTERM）。

### 11.2 修复

新增 `scripts/serve.sh`（start / stop / restart / status / logs / stop-orphan），
用 `setsid` + `nohup` 让进程**脱离会话**（实测 PPID=1），并记录 PID 便于管理。

### 11.3 顺带修掉一个假成功

`serve.sh` 初版只看「端口有响应」就报成功——结果端口被**别的残留进程**占着时，
自己的进程已经因「端口被占用」秒退，它却报了 ✅。

现改为三重校验：
1. 启动前检查端口是否被**别的** PID 占用，占用则拒绝启动并指出占用者
2. 启动后确认**自己启动的 PID** 仍存活
3. 再确认端口上的服务**确实是该 PID**（`lsof -t` 比对）

另加 `stop-orphan`：只结束命令行含 `nhx_app/server.py` 的进程，不误伤别的程序。
